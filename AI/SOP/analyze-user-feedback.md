# 第三类 · 可复用工作流 · 分析用户反馈并推进到完成

> 从某次具体任务抽象出的可复用流程。当流程经历实战后，在 `## 实例` 区回填。

## 写入规则（AI 必读）

1. **写什么**：触发条件、编号步骤、每步的命令或检查点、产出物、pitfalls、验证方式。
2. **不写什么**：一次性细节、特定文件路径硬编码（用占位符）、敏感值。
3. **抽象时机**：当某个流程被验证过一次且判断"下次还会再做"时，从 `Projects/` 的具体记录抽象到本文件。
4. **更新方式**：步骤有改进时直接 `patch` 替换；pitfalls 只增不删，标注 `（已解决 YYYY-MM-DD）` 或 `（仍有效）`。
5. **与 Projects 的关系**：每次用本 SOP 完成一次任务，在 `Projects/customer-research.md` 的进展条目里反向链接到本文件。

## 适用范围

用户反馈一类问题（bug、需求、体验吐槽）后，需要把它从"一句话反馈"推进到"已修复/已实现且真机验证通过"的全流程。适用于 AlgerMusicPlayer 及类似 HarmonyOS 原生项目。

## 触发条件

- 用户描述了一个现象/痛点/期望，但未给出明确技术方案。
- 反馈信息可能不全（缺复现步骤、缺环境、缺预期）。
- 需要先收敛成可执行任务再动手。

## 流程步骤

### 1. 收敛反馈 → 明确任务

- 用一句话复述用户的核心诉求，回给用户确认。
- 若反馈含多个点，拆成 N 个独立任务，按"阻塞 > 高频 > 易实现"排序。
- 标注信息缺口：缺复现步骤？缺环境？缺预期结果？缺验收标准？
- **不擅自补全**——缺口明确回给用户问，不猜。

### 2. 定位与复现

- 先用工具（`search_files` / `read_file`）在代码里定位相关模块，不靠记忆。
- 在真机上复现一次，记录现象（截图/HDC 日志）作为基线。
- 若无法复现，明确说"暂未复现"，不假装复现成功。

### 3. 根因分析

- 顺调用链往上追，找到根因而非症状点。
- 检查同模块的兄弟调用路径是否有相同缺陷（修类，不只修报错点）。
- 区分"代码 bug" / "需求未实现" / "设计取舍"——前两者要改，第三种要跟用户确认。

### 4. 实现修改

- 只改任务范围内的事，不做 drive-by 重构/改名/重排格式。
- 改完自检：新增的 import 是否真的需要？是否引入了未使用的依赖？
- 保留原作者语气和风格，只修正结构、事实、可执行性。

### 5. 构建与验证

- HarmonyOS 项目：`hvigorw assembleHap`（或项目实际构建命令）构建签名 HAP。
- 真机安装：`hdc install <hap路径>`，启动应用。
- 验证修复点：用步骤 2 的复现路径再走一遍，确认现象消失。
- 抓真机日志：`hdc hilog | grep <包名或关键字>`，确认无新增异常。

### 6. 沉淀

- 把本次进展写入 `Projects/customer-research.md` 的 `## 进展` 顶部。
- 若流程有新的 pitfalls，补到本文件 `## Pitfalls`。
- 若流程本身被改进，`patch` 本文件的步骤。
- 问用户："本次是否有需要沉淀到 preferences 的稳定偏好？"

## 产出物

- 修复后的代码（已提交，不擅自推送）
- 构建产物（签名 HAP）
- 真机验证证据（启动成功 + 日志无异常）
- `Projects/` 里的进展条目
- 可选：本 SOP 的 pitfalls 更新

## Pitfalls

- **复现不成功就动手**：容易改错地方，浪费时间。先确认能复现或明确"暂未复现"。（仍有效）
- **只修报错点不修类**：兄弟路径有同样缺陷，用户换个入口又触发。要顺调用链检查同类问题。（仍有效）
- **本地构建成功就报"完成"**：HarmonyOS 必须真机安装启动才算验收，构建成功≠运行正常。（仍有效）
- **HDC 连接不稳**：HoKit/HDC 偶尔断连，先 `hdc list targets` 确认设备在线再操作；断线重连后再继续。（仍有效）
- **音源 API 失效**：`music-api.gdstudio.xyz` 是第三方聚合接口，可能因上游限流或下线导致搜索/播放失败；排查前先确认是 API 侧还是本地代码侧问题。（仍有效）
